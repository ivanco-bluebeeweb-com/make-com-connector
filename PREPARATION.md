# Make.com Connector — Preparation

**Статус:** planning (до кода)
**Владелец продукта:** vlad@bluebeeweb.com
**Дата подготовки:** 2026-08-18, v0.1
**Почему сейчас:** в портфеле Imperal уже есть коннекторы к внешним
платформам, построенные по одному и тому же паттерну (пользователь
вставляет свой API-ключ/токен, коннектор дальше читает/пишет от его имени;
см. `se-ranking-connector`, `dataforseo-connector`, `wordpress-hub`). Make.com
(бывший Integromat) — крупная no-code automation платформа, которую
пользователи Imperal уже используют для склейки внешних сервисов между
собой; сейчас между Imperal и Make.com нет моста в обе стороны — ни
"дай Webbee посмотреть/запустить мои сценарии Make", ни "пусть события
Imperal триггерят сценарий в Make через webhook". Это следующий логичный
шаг расширения экосистемы интеграций, а не гипотеза без спроса — но сам
спрос (см. раздел 11) ещё предстоит подтвердить, а не считать доказанным.

---

## 1. Паспорт приложения

**Название в Marketplace (display_name): просто «Make.com»** — решено
2026-08-18. Внутренний app_id/папка остаются `make-com-connector`; в
карточке маркетплейса, установке и чате видно только «Make.com», без
слова «Connector» (по аналогии с тем, как «Notion Connector»/«Trello
Connector» всё же несут слово Connector — здесь осознанно короче,
как решил Влад). Проверено: `search_marketplace` по «Make.com» и по
общим терминам automation/workflow/webhook не нашёл ни одного
существующего или похожего приложения — дублей нет.

**Make.com Connector** — коннектор к Make.com Web API v2. Даёт Webbee
возможность от имени пользователя читать и управлять его сценариями Make
(list/run/activate/deactivate), видеть их последние выполнения, и
регистрировать/вызывать вебхуки (hooks) Make — то есть закрывает мост в
обе стороны: "покажи мне мои сценарии Make" и "дёрни вот этот сценарий
из Imperal".

Владелец продукта: vlad@bluebeeweb.com. Связанного события/pilot нет —
это плановое расширение линейки коннекторов, а не подготовка к конкретной
дате.

## 2. Проблема в человеческих словах

Когда **пользователь Imperal, который уже строит автоматизации в
Make.com**, сталкивается с **необходимостью проверить статус своих
сценариев или запустить один из них вручную**, ему приходится
**переключаться в отдельную вкладку/приложение Make, логиниться туда и
искать нужный сценарий среди списка вручную**, из-за чего теряется
контекст (Webbee уже знает, что произошло на сайте/в CRM/в почте, но не
может сама замкнуть цепочку и дёрнуть автоматизацию в Make) и появляется
лишний ручной шаг там, где мог бы быть один запрос на естественном языке.

Отдельная, вторая сторона той же проблемы: когда **событие происходит
внутри Imperal** (например: пришёл лид, обновился заказ, завершился
аудит), человек, который хочет **завести на это событие свою логику в
Make** (мультиканальные уведомления, синк в третьи системы, которых у
Imperal нет коннектора), сегодня не может это сделать нативно — только
через сторонний webhook-костыль вне продукта.

**Запрет соблюдён:** проблема сформулирована как "нет моста между двумя
живыми рабочими процессами пользователя", а не как "нужен API-коннектор".

## 3. Пользователи, роли и права

Единственная реальная роль на старте — **владелец аккаунта Make (тот же
человек, что подключает Imperal)**:

- **Job to be done:** видеть и управлять своими сценариями Make из
  Webbee; передавать события Imperal в Make через вебхук.
- **Данные, которые ей нужны:** список её сценариев (имя, активен/нет,
  team/organization), последние выполнения (успех/предупреждение/ошибка),
  список её hooks/webhooks.
- **Что может делать:** просматривать сценарии и их выполнения; запускать
  сценарий вручную (`POST /scenarios/{id}/run`); включать/выключать
  сценарий (`start`/`stop`); создавать webhook (hook) на своей стороне,
  чтобы Imperal мог его вызывать.
- **За что отвечает:** сама решает, какой сценарий запускать и когда —
  Webbee не запускает сценарий Make самостоятельно без явной команды
  (см. раздел 10).

Множественных ролей (например, "агентство ведёт клиентские Make-аккаунты")
на P0 не предполагается — это возможное расширение, отмечено в roadmap
(раздел 12) как гипотеза, требующая отдельного discovery.

## 4. Сценарии и точки решения человека

### Сценарий A — просмотр и ручной запуск сценария Make из Webbee

```text
триггер: пользователь спрашивает "какие у меня есть сценарии Make" или
         "запусти сценарий X"
  → действие человека: указывает, какой сценарий (по имени/team)
  → действие приложения: list_scenarios (GET /scenarios) находит сценарий,
    показывает статус (активен/пауза/ошибки), при команде "запусти" —
    run_scenario (POST /scenarios/{id}/run)
  → review человека: подтверждает запуск ИМЕННО этого сценария (см.
    раздел 10 — explicit confirmation обязательна перед run)
  → результат: executionId возвращён, статус выполнения показан
```

- **Happy path:** сценарий найден, запуск проходит, `status: 1` (success).
- **Missing/error path:** сценарий не найден по имени → показать список
  похожих; API вернул `status: 3` (error) → показать это как есть, не
  придумывать причину сверх того, что вернул Make.
- **Blocked state:** team/organization на паузе из-за превышения лимита
  операций — Make сам возвращает это как отдельную ошибку (задокументировано
  в `POST /scenarios/{id}/run`) — транслируется пользователю как есть.
- **Recovery path:** пользователь может позже повторить запуск или
  посмотреть детали через `replay` конкретного execution.
- **Точка решения человека:** какой именно сценарий запускать и когда —
  Webbee никогда не выбирает это самостоятельно.

### Сценарий B — событие Imperal триггерит сценарий в Make (исходящий webhook)

```text
триггер: в другом приложении Imperal происходит событие (напр. новый лид
         в sales-strategy-hub)
  → действие человека: заранее один раз указывает URL своего Make-вебхука
    (hook.make.com/...), который он сам создал в Make
  → действие приложения: коннектор делает HTTP POST на этот URL с
    payload события
  → review человека: нет — это fire-and-forget по дизайну самого Make
    webhook (как и остальные вебхуки в портфеле, напр. WooCommerce webhooks
    в wordpress-hub)
  → результат: сценарий Make получает данные и начинает свою логику
```

- **Happy path:** POST доставлен, Make отвечает 200.
- **Missing/error path:** URL недоступен/невалиден → лог ошибки доставки,
  видимый пользователю (по аналогии с `list_registered_webhooks`/
  `get_webhook` в wordpress-hub — статус видим, не скрыт).
- **Blocked state:** нет.
- **Recovery path:** пользователь может вручную повторить последнюю
  отправку (retry), если она не удалась.
- **Точка решения человека:** сам URL webhook — вставляется пользователем
  явно, не подбирается и не угадывается приложением.

## 5. Ценность и измеримый результат

**Ценность:**
- Не переключаться в отдельную вкладку Make, чтобы проверить статус
  автоматизации.
- Замкнуть цепочку "событие в Imperal → действие в Make" без стороннего
  Zapier-подобного костыля.

**Измеримые критерии успеха (P0):**
1. Пользователь может подключить свой Make-аккаунт (валидный API-токен)
   без ошибок с первой попытки.
2. `list_scenarios` возвращает реальный, актуальный список — без ложных
   расхождений с тем, что видно в самом Make.
3. `run_scenario` выполняет ИМЕННО тот сценарий, который назвал
   пользователь — 0 случаев запуска не того сценария.
4. Доставка исходящего webhook видна пользователю (успех/ошибка), не
   молчаливая.
5. Отсутствие спроса = неуспех: если после публикации ни один
   реальный пользователь не подключит свой Make-аккаунт за разумный срок
   (число определяется на discovery, см. раздел 11) — гипотеза не
   подтвердилась, и P1/P2 не начинаются.

## 6. Границы: делает / не делает

**Делает (P0):**
- Подключение через личный Make API token пользователя (см. раздел 7).
- `list_scenarios`, `get_scenario`, `list_scenario_executions`-подобный
  просмотр статуса (через `usage`/execution status, где доступно нативно).
- `run_scenario` (с explicit confirmation), `activate_scenario`,
  `deactivate_scenario`.
- `list_hooks`/`create_hook` для просмотра/создания webhook на стороне
  Make команды.
- Отправка исходящего HTTP POST на webhook URL, который пользователь сам
  указал (Imperal → Make).

**Не делает (P0):**
- Не создаёт и не редактирует сами сценарии (blueprint) — это первичное
  проектирование логики остаётся в UI Make, слишком рискованно и
  бессмысленно пересобирать визуальный no-code редактор текстом.
- Не управляет billing/organization/team-настройками Make.
- Не даёт Webbee самостоятельно, без команды, запускать сценарии по
  расписанию или в фоне — только по явному запросу пользователя.
- Не хранит и не пересылает payload'ы вебхуков третьим лицам вне
  выбранного пользователем Make-адреса.

**Рискованные действия под явным запретом:**
- Автоматический массовый запуск/остановка нескольких сценариев без
  построчного подтверждения каждого — по аналогии с bulk-паттерном
  `preview_*` → `apply_*`, уже принятым в `wordpress-hub`.

## 7. Данные, конфиденциальность и интеграции

- **Минимально необходимые данные:** Make API token пользователя (личный,
  из его профиля Make → API tab, см. официальную документацию); team/
  organization ID для фильтрации сценариев.
- **Источник данных:** Make.com Web API v2 (`https://<zone>.make.com/api/v2`,
  зона зависит от региона аккаунта пользователя — `eu1`/`eu2`/`us1` и т.д. —
  **неизвестно / требует discovery**, каким образом надёжно определять
  зону пользователя при подключении).
- **Что хранится:** сам API token (зашифрованно, по тому же паттерну, что
  и остальные коннекторы — сравнимо с DataForSEO login+password); список
  подключённых scenario ID, на которые пользователь ссылался, — для
  быстрого повторного поиска по имени.
- **Что остаётся ссылкой/внешним источником:** содержимое сценариев
  (blueprint), содержимое execution-логов — читается по запросу, не
  зеркалируется локально.
- **Retention:** сам token хранится до explicit disconnect (по аналогии с
  `disconnect_dataforseo`); история запусков, инициированных из Webbee,
  хранится для трассируемости (кто/когда попросил запустить сценарий).
- **Tenant isolation:** один токен = один Make-аккаунт = один пользователь
  Imperal; не шарится между тенантами.
- **Что нельзя отправлять третьим сторонам:** сам API token никогда не
  логируется и не возвращается в чат целиком (по аналогии с
  `list_application_passwords` в wordpress-hub — "никогда сам секрет").
- **Интеграции и их статус:**
  - Make.com Web API v2 (scenarios, hooks) — `available` (публичная,
    задокументированная, аутентификация по personal API token подтверждена
    в официальной документации Make Developer Hub).
  - Определение региональной зоны (`eu1`/`us1`/...) аккаунта пользователя
    при подключении — `unverified`, требует проверки на реальном
    аккаунте с реальным токеном.
  - AI Agent scenarios (`GET /scenarios/ai-agents`) — `not needed for P0`,
    отдельная более новая часть API Make, не входит в первый срез.

## 8. P0 — минимальный законченный полезный путь

**Главный use case:** пользователь подключает свой Make-аккаунт, видит
список своих сценариев из Webbee, и может явно попросить запустить
конкретный сценарий или включить/выключить его — без переключения в
отдельную вкладку Make.

**Сущности и действия, без которых результат невозможен:**
- Подключение (`connect_make`) — сохранение личного API token.
- `list_scenarios` — реальный список с именем/статусом.
- `run_scenario` — с explicit confirmation.
- `activate_scenario`/`deactivate_scenario`.

**Server-side safety gates:**
- Токен не в открытом виде ни в одном ответе после сохранения.
- `run_scenario` требует явного подтверждения конкретного сценария по
  имени/ID перед вызовом (нельзя угадывать "наверное, вот этот").

**Сознательно исключено из P0:** редактирование blueprint, управление
несколькими Make-организациями одновременно, входящие вебхук-триггеры
внутрь Imperal (только исходящие, из Imperal в Make).

**Acceptance criteria простыми словами:** пользователь один раз вставляет
токен → видит настоящий список своих сценариев → просит запустить один
из них по имени → получает реальный результат выполнения (успех/
предупреждение/ошибка), а не выдуманный.

## 9. UX-карта Imperal panel

**Решено с Владом 2026-08-18:**
1. **Первый экран приложения = форма подключения** (не список сценариев,
   не онбординг-карусель) — пользователь видит поле для токена сразу при
   первом открытии панели, если аккаунт ещё не подключён.
2. **Подсказка "где взять токен" — по кнопке, во всплывающей панели**, не
   инлайн-текстом под полем. Кнопка "Как получить токен?" рядом с полем
   token → открывает отдельный center-overlay dialog с инструкцией внутри.
   Технически это уже проверенный, реально работающий в проде паттерн —
   такой же, как `yt_connect_dialog` (Youtube Studio) и `wp_ssh_dialog`
   (WordPress Hub): отдельная `@ext.panel(slot="center", center_overlay=True)`,
   вызываемая через `ui.Call("__panel__make_connect_help")`, возвращающая
   `ui.Dialog(title=..., content=..., confirm_label="", cancel_label="Close")`.

- **Точка входа:** новая карточка коннектора в Marketplace/panel, как у
  остальных внешних интеграций (se-ranking-connector, dataforseo-connector).
- **Первый экран:** форма подключения — поле для Make API token + кнопка
  "Как получить токен?" открывает popup-инструкцию (Make → Profile → API →
  Add token, по официальной документации Make Developer Hub), кнопка
  "Проверить и подключить" отдельно.
- **Primary next action** после подключения: список сценариев с их
  статусом (активен/на паузе/invalid).
- **Empty state:** "У вас пока нет сценариев в этом Make-аккаунте" —
  честно, если список реально пуст.
- **In-progress state:** во время запуска сценария — явный лоадер, статус
  меняется на "запущен, ожидаем результат" (учитывая, что API может не
  успеть ответить синхронно за 40 секунд — `responsive: true/false` в
  самом Make API).
- **Blocked state:** team/organization на паузе (операционный лимит
  превышен) — показывается как есть, с текстом из ответа Make.
- **Ready-for-review / approved states:** не применимо на P0 (нет
  многошаговых approval-цепочек, запуск сценария — разовое действие с
  explicit confirmation, не approval workflow).
- **Ошибки и recovery:** невалидный токен → явное сообщение с ссылкой на
  то, где его перевыпустить в Make; сценарий не найден → показать похожие
  по имени.
- **Где виден результат:** прямо в чате Webbee (statuses/executionId) и
  в панели коннектора (список последних запусков).
- **App settings:** обязательная secondary-кнопка в сайдбаре по
  `UI_INTERFACE_STANDARD.md` — реальные настройки (напр. дефолтный
  team/organization ID, если у пользователя их несколько), сохранение
  через write-вызов с зелёным подтверждением.

## 10. Safety, approvals и audit trail

- **Что Webbee может выполнить сама:** чтение списка сценариев, hooks,
  статусов выполнения — без подтверждения (read-only, безопасно).
- **Что она может только предложить:** запуск конкретного сценария по
  косвенному запросу ("может, стоит запустить X?") — не выполняет
  самостоятельно.
- **Explicit confirmation обязательна для:** `run_scenario`,
  `activate_scenario`/`deactivate_scenario`, `create_hook`, отправка
  исходящего webhook на новый (ранее не подтверждённый) URL.
- **Named human approval:** не применимо на P0 — нет multi-party
  approval-цепочек, только один владелец аккаунта.
- **Audit trail (обязательно логируется):** кто (Imperal user) и когда
  попросил запустить/остановить/активировать сценарий, executionId,
  итоговый статус (success/warning/error) — по аналогии с тем, как
  `list_order_notes`/`get_scheduled_action` в wordpress-hub делают
  прослеживаемым каждое действие.
- **Fail closed:** если токен невалиден или Make API недоступен —
  никакое действие не выполняется молча; ошибка показывается как есть.

## 11. Discovery и проверка гипотезы

**До расширения за P0 нужно проверить:**
- Кого интервьюировать: реальных пользователей Imperal, которые уже
  используют Make.com (можно найти через опрос в существующей базе
  клиентов — конкретный список пока не собран, это первый шаг).
- Вопросы: как часто они вручную заходят в Make проверить статус
  сценария; какие события Imperal им хотелось бы прокидывать в Make;
  используют ли несколько Make-организаций одновременно (это определит,
  нужна ли multi-org поддержка раньше, чем предполагалось).
- Реальные, но обезличенные артефакты: 2–3 примера типичных сценариев
  Make, которые пользователь хотел бы дёргать из Webbee.
- Сколько интервью достаточно для следующего решения: **неизвестно /
  требует решения продукта** — не менее 3 реальных пользователей Make
  до начала P1, чтобы не строить multi-org/входящие-триггеры на
  умозрительном спросе.

**PRE-PANEL CHECKLIST — пройдено для каждого компонента в дереве:**
- `ui.Password` — без `label=`, без `type=` ✅
- `ui.Button` — стандартные props, `on_click=ui.Call(...)` ✅
- `ui.Call("__panel__make_connect_help")` — вызов center-overlay панели по
  id, тот же паттерн, что и `ui.Call("__panel__yt_settings2")` в Youtube
  Studio ✅
- `@ext.panel(..., slot="center", center_overlay=True)` — обязательный
  `center_overlay=True`, иначе панель не будет получена (dead slot) ✅
- `ui.Dialog` — `content=` принимает один UINode (здесь `ui.Stack`), не
  список напрямую ✅
- `ui.Form` — не путать с предзаполненными `value=` (тут не нужно, ввод
  ручной) ✅
- `ui.Link` — `label=`/`href=`, не `text=` ✅

**Осознанно НЕ используем `ui.Tooltip` для этой подсказки** — Tooltip это
hover-эффект (наведение мышью), а решение Влада было явно "по кнопке, во
всплывающей панели" — то есть клик → модальное окно (`ui.Dialog`), а не
hover-балун. Технически иное поведение, не взаимозаменяемо.
